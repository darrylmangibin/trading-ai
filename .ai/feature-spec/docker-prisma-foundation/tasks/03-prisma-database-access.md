## Objective

The API exposes a lazy, reusable Prisma database boundary and a guarded local schema/client workflow without coupling process liveness to PostgreSQL.

## Background

Depends on: Task 01

The API currently has no persistence provider. This task owns the model-free schema, tooling configuration, generated-client contract, and lazy provider. Use the NestJS and NestJS best-practices skills, preserving project ESM and explicit injection/factory patterns.

## Scope

### In Scope

- User-installed Task 03 packages, Prisma configuration, generated output placement, migration target validation, and API database module lifecycle.
- Hermetic real-AppModule HTTP characterization before provider wiring; existing ConfigModule remains the application configuration owner.

### Out of Scope

- Application entities/migrations, eager database startup checks, diagnostic CLI, database test harness, Docker app services, or product endpoints.

## What to Implement

### 1. Establish Prisma tooling and schema boundaries

- Have the user install the exact Task 03 dependencies. Add the PostgreSQL model-free schema and ESM `prisma-client` generator under the paths in the design.
- User-run installations from the repository root:

```powershell
npm install --save-exact --workspace @trading/api @prisma/client@7.10.1 @prisma/adapter-pg@7.10.1 pg@8.23.1
npm install --save-dev --save-exact --workspace @trading/api prisma@7.10.1 @types/pg@8.23.1 dotenv@18.0.8
```

- Generate TypeScript to `src/generated/prisma` with compiled `.js` import suffixes. Add appropriate Git/lint/format exclusions; never hand-edit generated files.
- Add explicit generate/validate/migrate scripts using `prisma7.config.ts`. CLI configuration may load its own environment quietly; generation works without database credentials.
- For migration development, derive preflight mode from the invoked Prisma command, validate local development/shadow endpoint identities, require `trading_shadow`, and reject shared/test/alias-equivalent targets before Prisma work. Do not add a bypass flag or CREATEDB fallback.
- Document user-performed generation, reviewed migration creation/application, and no automatic startup mutation. No product migration is created in this task.

### 2. Add lazy access and preserve liveness

- Introduce focused database config/factory/provider/module files, using ConfigService through explicit injection or a factory. Do not construct the adapter, require DB credentials, or connect during module initialization.
- Create one client on first requested database work; reuse it; close only an allocated client through the existing shutdown lifecycle.
- Validate database URL syntax on database use and return typed safe errors. Do not log raw connection strings or driver errors.
- Before changing module wiring, extend real-AppModule HTTP characterization for missing, malformed, and unreachable DB configuration. Set test environment before imports and ignore environment files in test mode.

## Contracts

Follow the cited System Design sections; do not duplicate or silently change their contract.

- **Data**: No application records; one process-local lazy client and explicit migration configuration.
- **Inputs**: ConfigService database configuration or explicit CLI environment; approved schema/generator settings.
- **Outputs**: Validated lazy client, generated source, safe configuration errors, and unchanged liveness.
- **Validation**: Syntax and safe errors at DB use; local distinct shadow/development targets before migration commands.
- **Compatibility**: Existing API prefix/CORS/health, startup without a database, ESM imports, and generated-file ownership.

## Acceptance Criteria

1. The user can explicitly generate and validate an empty-model client; compiled API imports work and schema/migration workflows identify their local development/shadow targets. (AC-5)
2. Database access allocates at most one client lazily and releases it; invalid or unsafe migration configuration fails without executing database work or exposing secrets. (AC-5, AC-13)
3. Real AppModule liveness/prefix/CORS behavior remains intact with absent, invalid, and unreachable DB configuration. (AC-9)
4. Applicable lint, typecheck, format, and wiring/build checks pass; unavailable roles are reported accurately.
5. Record files, verification evidence, and current status in the feature tracker; only /check marks completion.
